The situation

PISA Consulting's three leadership assessments existed as self-contained HTML files. Everything ran inside the visitor's browser: the statements, the scoring rules and the report content sat in the page, the report was a print dialogue and the email was a mailto link, so an answer set lasted only as long as the tab stayed open. The firm wanted the same instruments as a hosted product, with the scoring done on a server and the results retained.

What I built

The assessment, from sign-in to printed report

A participant registers, confirms their email, completes a profile and is granted access to one or more instruments. They work through the statements in the browser with answers held locally so a closed tab does not cost them the session, review what they have entered, and submit. The server scores the submission, bands it and builds the report, which they can read on screen, print or download. Three instruments are live, the largest running to 96 statements.

Scoring rules taken out of the page and put in the database

Before writing any engine code I transcribed all 250 scoring rules across the three instruments, 85, 91 and 74, each one carrying the line of the original file it came from. That ledger became the specification for the rebuild. Scoring logic, band thresholds and the coaching text now live as seeded database rows read by an edge function rather than in page source. That move was the commercial point of the build.

Accounts, access control and an admin console

The portal carries registration, email confirmation, login, password recovery, profile completion, access-token entry and an email challenge, alongside a client area for results history, report detail, notifications and settings. The admin side issues and tracks access, views results and analytics, and manages client profiles. Roles for participant, manager and administrator are enforced in Postgres with row-level security rather than by hiding React pages, and the access-link model supports replacement links. Authentication was consolidated onto a single provider.

Records that cannot be quietly edited

Consent is written to a hash-chained ledger with a single edge function as the only write path, and direct write grants on the table revoked. Result revisions are append-only, and I exercised the trigger rather than trusting that it existed: an insert accepted, an UPDATE refused, a DELETE refused, then the whole exercise rolled back leaving no rows behind. The lesson, that a trigger never exercised is not a trigger that works, is written up in the project's own learnings folder.

Live inside the client's existing website, with that site proven untouched

The build ships as a static bundle uploaded into a folder under the client's existing WordPress installation, which a WordPress routing rule allows without editing anything at the root. After go-live I proved the installation unaffected four separate ways, including an md5 check confirming the root .htaccess was byte for byte what it had been, and a check that WordPress itself still served 200. The deploy is verified by rebuilding the committed source and reproducing the exact content-hashed bundle the live URL serves, with 5 of 5 routes returning 200.

The client's existing site mirrored, run locally, and changed under control

Their live WordPress site is the client's own, not something I built, and I took a full copy of it: 29,196 files and 6,485 directories, every file checked against the server's own listing with 0 missing and 0 size mismatches, plus a database dump of 29 tables and 8,634 rows test-restored into a throwaway database and matched against production. That copy runs locally under Docker Compose with WordPress, MariaDB and WP-CLI, and it is where a new privacy policy was prepared before it went anywhere near production. A rollback dump was taken first, the text was extracted from the source PDF with PyMuPDF and checked word for word rather than retyped, then six changes were applied and verified live at 14 of 14 sections, 22 of 22 numbered items, the footer pointing at the page and not the old file, and all existing pages still returning 200.

The hard part

Proving a rebuilt scoring engine returns the same answer as the original, not a similar one

The client's three instruments already worked, so rebuilding them was only worth doing if the new engine returned the same result on every input, and a report that places someone one band away from where the original placed them is worse than no report at all. The check lives at tools/parity-gauntlet/ and drives both products in a real browser rather than comparing two functions in isolation: 15 deterministic answer patterns per instrument, 45 in total, with the new system's answers read back out of the database rows they were actually stored in, returning 0 answer mismatches, 0 order differences and 0 percentage differences. A second pass searched below, at and above every band cut on all three instruments, 36 vectors in total, and ten of the twelve just-below vectors land a float hair under their cut, so they round to the displayed percentage of the band above while correctly banding below it, and both products placed every one of them on the same side. Report prose was then diffed across 81 pairs, with no authored content missing and no unexplained extra lines. Because a harness written by the same person who wrote the engine proves less than it appears to, three independent review agents, blind to the build, were given the originals and the rebuild and asked to produce a counterexample rather than to agree, across 29 paired runs, and all three returned NO_COUNTEREXAMPLE. The same standard closed the deployment: rebuilding the committed source reproduced the exact content-hashed bundle the live URL serves, 5 of 5 routes returned 200, and the screenshot protocol was changed so the page prints its own URL, its loaded bundle hash and a timestamp into the frame before capture, which ties an image to one specific production build instead of to a moment in time. One defect the test suite never caught came out of driving the live URL by hand: a routing branch still tested identities for the old authentication provider's prefix, so every real client under the new provider was sent to a dead-end screen, and separately I found 16 test files that had never run under any runner, wrote the runner, and made them real.
