Board-based CRM for a sales team

Client
A South African IT retailer (anonymised)
Sector
CRM, sales operations and task management
Built
June 2026 to September 2026
Role
Sole engineer on the custom work, design through production
Status
In production, not publicly linked

A sales team runs its day out of one place. Work sits on boards as cards, each card can point at the customer it belongs to, and anything with a date on it chases the person responsible instead of waiting to be remembered. Mail arriving from outside can be turned into a card on the same board, and each person gets their own calendar feed of what is due.

The situation

The open-source CRM this was built on holds leads, people, organisations and quotes across nineteen packages, and not one of them is a task system, so the work itself had nowhere to live next to the record it belonged to. The job was to put the board and the customer record in the same application, delivered as a single-tenant deployment under the client's own branding.

What I built

A task board built into the CRM itself

The Board package is a task system in its own right: boards with lists, drag-and-drop cards, board members and roles, and one pill switcher across Boards, Table, My Day, My Calendar, Assignments and the overdue views. Cards carry a priority, a start date, a due date and a separate plan date for when you intend to do the work, plus checklists, colour labels, task types, comments with mentions, attachments, covers and blocked-by dependencies. Every board has a capture rail for getting something written down before deciding where it belongs. It is 123 files and 36 models with its own migrations and permission keys, and none of it exists in the open-source base I started from.

Cards that point back at the customer

A card can be linked to a lead, a person, an organisation or a quote through one polymorphic card_links table. The lead and person detail pages then carry a reverse Linked Cards panel, filtered by board membership, so opening a customer shows the work in flight against them and opening the work shows the customer. That is the part a general-purpose board tool cannot do, because the board tool does not hold the sales record, and it is why the work sat inside the CRM rather than beside it.

Work that chases the person, not the other way round

Each card can carry two reminders, one for the due date and one for the plan date, fired by a five-minute cron with idempotent stamps so a reminder that has fired is not fired again, with bell-only due-soon pings going to the owner, the members and the watchers. Recurring cards support daily, weekly by weekday mask, monthly, every-N, wait-for-completion and skip-overdue rules. Board automations fire on due-in-N-days and overdue-by-N to move a card, set its priority or notify someone, with a one-fire-per-card ledger behind them. My Calendar gives each person their cards and CRM activities as a personal calendar with a signed public ICS feed, so it can be subscribed to from an ordinary calendar app.

Each person's own mailbox, and email that becomes a task

Every user connects their own IMAP mailbox, with the mailbox password encrypted at rest and pinned by its own test. Inbound mail is polled, MIME headers are decoded, and the sender is matched automatically to the right person or lead, then a Create task action turns the email into a due-dated card stamped with the source email it came from. Ownership scoping keeps one person's mail out of another person's view and is pinned by five dedicated tests, including MailUserScopeTest and PerUserSyncOwnershipContractTest. There is a shared-mailbox model as well, for the addresses several people read together.

Tasks arriving by WhatsApp

A WhatsApp lane was built so a task could be sent from a phone without opening the CRM: a webhook controller receives the message, a name matcher works out which user and which card it belongs to, and a sweep command clears pending instructions that arrived while the app was not listening. The webhook lane was deployed and proven on production once, and a second transport against the WhatsApp Cloud API exists in source alongside it, with the terms and privacy pages that review path needs served by the app itself. I do not claim the channel is up today. What I do claim is that when the provider stops reporting, the board says so in plain words rather than silently swallowing the tasks.

Getting people onto it, and getting releases onto the server

An invite sends an activation email and the account stays inactive until the invitee opens the link and sets their own password, and the modal says that out loud. A test named UserInviteTruthfulnessTest checks the promise in that copy against what the code actually does. The host is deliberately plain: shared hosting with no Node, no websockets and the crontab CLI disabled, so the scheduler runs from a control-panel entry every minute and the visual redesign ships as scoped styles rather than recompiled Tailwind utilities. Production is not a git repository, so releases go up as curated file uploads written to a .new path and moved into place atomically, followed by a cache clear, with a timestamped backup taken first and a standing hash check between production and the repository before any upload.

The hard part

A reminder bug the test suite could not see, by construction

Card reminders were sliding two hours earlier every time somebody saved the card. The reminder columns were written to the database as true UTC instants but read back through Laravel's plain datetime cast, which interprets a stored value in the application timezone, and those two only agree when the application timezone is UTC. My development machine ran UTC and production runs Africa/Johannesburg, so the local suite could not fail on this: every test passed on a box where the defect does not exist, while each save re-read the stored instant as local time and wrote it back two hours earlier, compounding. The fix was a dedicated cast, Webkul\Board\Casts\UtcDateTime, pinning those columns to UTC regardless of what app.timezone says, plus a guard that refuses to arm a reminder in the past so a drifted value cannot quietly become a dead one. Three further defects came out of the same asymmetry and were fixed in the same commit. It is locked by tests/Feature/ReminderTimezoneTest.php, 21 cases green, 7 of the new ones red if the cast is removed. The lesson I kept is that a green suite on a machine configured differently from production is not evidence, and the difference has to be put inside the test rather than assumed away.

How it was proven
  • The timezone fix is locked by tests/Feature/ReminderTimezoneTest.php: 21 cases green, and 7 of the new ones go red if the UTC cast is removed.
  • The Board package is provably new rather than renamed. git ls-tree --name-only upstream/2.2 packages/Webkul/ lists 19 packages and Board is not one of them.
  • Authorship is separable from the fork. git shortlog -sn --all attributes 280 commits to me against a 4,431-commit history, and the merge base with upstream/2.2 dates my fork point to 21 May 2026.
  • The invite modal's promise is tested rather than merely written. UserInviteTruthfulnessTest checks the copy against the behaviour: the account stays inactive until the invitee sets their own password.
  • Mailbox ownership is pinned by five scope tests, including MailUserScopeTest, PerUserSyncOwnershipContractTest and SalesMailboxAclSplitTest, so one user's mail cannot surface in another user's view.
What this does not prove
  • No usage figures exist for this system. No user count, no revenue, no hours saved, no uptime number. None was ever measured and I am not going to invent any.
  • The base is open source and it is not my work. Krayin CRM is Webkul's, and so are the README, the changelog and the composer file still sitting in the repository. Mine is the 280 commits after a fork point dated 21 May 2026, and the Board package that has no upstream equivalent.
  • There is no public link here and no code to read. It is one client's production system on their own host, and the repository is private. I will walk through any of it on a call.
  • The product is positioned around agentic sales, but no AI layer is shipped. It was held back deliberately rather than faked, so I claim none of it.
