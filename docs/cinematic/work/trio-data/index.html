trio-data.co.za/careers

It takes a job application from the moment it arrives to a booked interview and a written report the firm can hand to its client. Recruiters see every applicant in one place regardless of how they applied, search for people in ordinary language, and send an invitation the candidate answers on a single screen without creating an account. The firm's public careers page is part of the same system, so a vacancy posted internally appears publicly and the application comes straight back.

The situation

Trio Data places agents inside client workforces to detect internal theft and fraud, so recruiting and vetting those people is the business itself and not a back-office chore. The public website was a classic ASP site run by a previous vendor, and the old tree is preserved in the repository with a manifest. What went in instead is one system that carries a CV from the inbox it lands in to a booked interview and a client-ready report, with the public site as an endpoint of that system rather than a separate brochure.

What I built

Four doors, one queue

CVs reach the firm four ways: a scheduled weekday mailbox scan, a live mailbox connected over IMAP or Microsoft Graph, a drag-and-drop upload of a PDF, DOCX or TXT file, and applications submitted on the public careers page. All four land in the same intake queue, so a recruiter never has to remember which channel a person came through. Each scan run is recorded as an inspectable job with its own history.

Classify before you spend

Every document is classified before anything is extracted from it, so a payslip or an ID copy is never parsed as a CV and never paid for as one. Image-only CVs, including the ones pasted into Word as a picture, go through OCR. Extraction is swappable: Gemini when a key is configured, on-device code when it is not, and the whole application runs end to end with no AI key at all. Every extraction writes its cost to a ledger, so the price of the AI path is a number I can show.

Finding the right person

Candidate records are structured: region, education, skills, experience, certifications, employment history and availability. Recruiters search in plain English, for example forensic auditors in the Western Cape with ten or more years, and match on geocoded travel distance using a cached geocoder with a manual override for the places a geocoder gets wrong. Duplicates are detected and resolved through a guarded merge. Matching and shortlisting against an open job order are persisted, so a shortlist survives as a record.

Interviews, including the days they go wrong

A recruiter invites, and the candidate either picks their own slot on a single page with no account and no login, or the recruiter books it firmly, with a double-book guard. The exceptions are modelled by name: interviewer unavailable, no-show, undo a no-show, reschedule, cancel, reassign. Scorecard templates and their criteria are configurable and an interview carries a review step, so what happened in the room is written down. Booking reminders run on a schedule.

Mail as a subsystem

Each user's mailbox credentials are set up inside the application through a wizard and stored per user, never as environment variables. Automated mail goes out from a system sender with its own identity, so a reminder is never sent from whichever recruiter happened to be logged in at the time. Templates render with a preview before anything leaves, bounces and non-delivery reports are drained back into the system, and every mailbox carries its own retention period in days.

Reports the firm can hand to a client

Trio Data's output has to stand up in a hearing, so the reporting side is built to a documentary standard rather than a dashboard one. There is an incident register with categories, assigned investigators and recommended actions, cross-incident pattern analysis, and escalation drafting. Vetting reports generate from templates and export to HTML, Markdown or plain text. Key findings reports are drafted with AI assistance, watermarked, produced with a separate client copy, and emailed out from the system.

The hard part

The platform is not reachable from the internet. The candidates are.

The recruitment platform runs on the client's own machines and is not reachable from the internet, which is the right posture for a system holding candidate vetting records. The people it has to talk to are on the open internet: someone applying for a job, someone choosing an interview slot. I built the exchange so the private app is always the client and never the server. Vacancies publish outward as a generated file deployed with the site. Applications land in a queue directory held outside the web root, so a candidate's CV never sits in a servable path, and the local app polls for them over HTTPS with a constant-time token check, ingests each record and then acknowledges it so the queue empties itself. Booking runs the same way in reverse, with the published context cut to the minimum a person needs in order to choose a slot, name, job, venue, window and free times and nothing else, and the app revalidates the slot atomically before it confirms, so two people cannot take the same time by racing each other. The failure worth recording here was a silent one: two machines each publishing the whole vacancy list and quietly overwriting each other. The fix was an explicit opt-out flag rather than an absent setting, because a path that is simply not configured reports skipped and logs nothing, which leaves switched off on purpose indistinguishable from misconfigured by accident.

How it was proven
  • Data retention was proven with a real delete rather than a dry run. The purge ran against a throwaway copy: 306 files removed and all 306 verified unreferenced, 219 kept because something still pointed at them, and a 9.5 MB candidate CV byte-identical afterwards.
  • Publishing to the public site was verified over the public internet with a cache-busted fetch, explicitly not the deploy script's own smoke test. Eleven of twelve live content markers passed and the careers feed was byte-identical by SHA-256 to an artefact captured from production beforehand.
  • 224 of the repository's 320 scripts are proof harnesses, under a rule written into the README: a user-facing change is only proven by observing it in a real browser, and passing tests and API 200s are interim signals, not completion.
  • A browser audit covering all 28 routes across three roles produced 181 evidence artefacts over four adversarial review rounds, and every finding was re-tested against live code before any fix was planned.
  • I ran an independent authorization audit of my own build and closed every confirmed finding. The real control is server side, 158 role guards in the API layer, with the client-side gate treated as convenience and not as control.
What this does not prove
  • No placement count, no candidate total, no hours saved and no cost saved. Nothing in the system measures any of it and no measurement exists on file, so there is nothing for me to quote and I am not going to invent it.
  • No testimonial, quote or reference exists for this work, and I have not written one.
  • The platform itself is not a public product and you cannot click into it. It runs on the client's own machines behind a private network by design. The careers site is the only part of it visible from outside.
  • No traffic, ranking or conversion figures for the public site. No analytics export exists, so there is nothing to quote.
